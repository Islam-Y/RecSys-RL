# Протокол проверки сигнала reward model — 2026-10-14

Зафиксирован до вычисления новых сравнений. [Конфигурация](../configs/reward-signal.json). Используется существующий checkpoint reward model, эпоха 4; нейросеть повторно не обучается. Предыдущий результат показал MSE выше персональной средней и завышение высоких прогнозов. Цель — отделить качество калибровки от способности различать кандидатов.

## Данные и границы

Прежние reward selection (14 039 пар) и validation (5 840 пар). Подбор преобразований выполняется только на selection; validation используется для отчёта. Она уже просматривалась на предыдущих этапах, поэтому новый результат является адаптивным продолжением исследования, а не независимой проверкой. Final test не читается для меток или метрик.

Контексты, кандидаты, метки, каталог, словарь пользователей, checkpoint и исходный reward-код проверяются по SHA-256. CLI расширяется новой командой; старые вычислительные модули сохраняются. Прогноз загруженного checkpoint сверяется с сохранённым исходным прогнозом, допустимая абсолютная разница ≤ 1e-6.

## Калибровка и персональная средняя

На selection подбираются:

1. Ограниченная аффинная калибровка `c = clip(a*p+b, 0, 1)`: OLS с неотрицательным наклоном; если оптимальный наклон отрицателен, используется постоянная средняя selection. Это отдельное преобразование фиксированной нейросети.
2. Смесь `h = u + alpha*(c-u)`, где `u` — средняя пользователя из раннего reward train с общей средней для неизвестных пользователей. Alpha минимизирует selection MSE и ограничена [0, 1].

Параметры фиксируются до оценки validation. Все варианты сравниваются с raw reward model, общей, пользовательской и трековой средней. Основная метрика — MSE; дополнительно MAE, RMSE, R² и калибровка. Для разницы MSE с пользовательской средней — парный cluster bootstrap по пользователям, 2 000 повторов, seed 42, percentile-интервал 95%. Вес внутри каждого повторения остаётся равным весу пар.

Неотрицательная калибровка и смесь с константой пользователя сохраняют порядок кандидатов одного запроса, кроме дополнительных равенств от clipping/нулевого наклона/alpha. Улучшение общей MSE после них не трактуется как улучшение выбора трека.

## Прямое различение кандидатов

Для запросов с несколькими наблюдавшимися целевыми треками сравниваются все пары кандидатов. Проверяется равенство user/timestamp/истории внутри запроса. При различии меток > 1e-6 правильный порядок получает 1, обратный — 0, равенство прогнозов в пределах 1e-7 — 0.5. Основной отчёт включает все такие сравнения; дополнительный — разрыв фактических долей ≥ 0.10.

Сравниваются raw/калиброванная/смешанная reward model, средняя по треку, пользовательская средняя и эвристика «короче сначала». Для постоянных прогнозов точность равна 0.5. Интервалы accuracy и парной разницы с трековой средней считаются cluster bootstrap по пользователям. Дополнительно сохраняется средняя accuracy с равным весом запросов.

Это различение треков при одинаковой наблюдаемой истории. Отклик на каждый из сравниваемых треков присутствует в данных, но порядок действий внутри одного округлённого timestamp неизвестен. Сравнение остаётся наблюдательным и условным на нескольких прослушиваниях, а не проверкой причинного эффекта рекомендации.

## Перемешивание кандидата

Для seeds 42, 43, 44 кандидат переставляется между размеченными парами:

- Внутри того же пользователя.
- Внутри того же пользователя и train-каталожного тертиля длительности.

История, ID пользователя и исходная метка сохраняются; embedding кандидата, его длительность и наличие в истории пересчитываются. Сохраняются доля реально изменённых кандидатов, MSE до/после на всех и изменённых парах. Это абляция входа: метка относится к исходному треку. Она не является фактическим откликом на подставленный трек и не используется как обучающий пример.

Перемешивание внутри длительности помогает проверить сигнал сверх грубой категории длительности, но не устраняет смещение наблюдений. Три seeds описывают вариацию перестановки, не случайность обучения модели.

## Вывод и воспроизведение

Положительный результат не объявляется доказательством пользовательской пользы. Для дальнейшего RL отдельно фиксируются функции reward, ограничение KL, бюджет и диагностики. При слабом сигнале RL может исследоваться как оптимизация ненадёжного прокси с явно указанными ограничениями; рост предсказанного reward не принимается за рост реального отклика.

```bash
python -m recsys_rl reward-signal --device auto
```

Непустой output не перезаписывается. В `outputs/reward-signal-v1/` сохраняются параметры преобразований, прогнозы, перестановки и полный JSON. Метрики пересчитываются по сохранённым прогнозам, проверяются хеши. Агрегированный результат после сверки публикуется в `experiments/reward-signal-result.json`. Исходная GPT-2, reward model и финальный test сохраняются.

# Протокол reward model — 2026-10-14

Зафиксирован до первого обучения reward model. Конфигурация: [reward.json](../configs/reward.json). Цель этапа — прогноз наблюдаемой доли прослушивания по пользователю, истории и треку, с оценкой на более поздних событиях. RL в этот запуск не входит.

## Метка и границы интерпретации

Источник — прежний `flat/50m/multi_event.parquet` из [Yambda](https://huggingface.co/datasets/yandex/yambda), проверяемый по SHA-256 исходного baseline. Используются только наблюдавшиеся события `listen` для исходных train/validation-запросов и их целевых треков. Отсутствие взаимодействия не превращается в нулевой отклик, случайные негативы не добавляются.

Метка события: `min(played_ratio_pct, 100) / 100`. Ноль допустим. Значения выше 100% означают возможное повторное прослушивание частей трека; ограничение единицей задаёт цель «доля прослушивания», а не исправляет эти события как ошибки. При нескольких событиях одного `(user, timestamp, item)` усредняются уже ограниченные доли. Одна такая пара имеет один вес независимо от числа повторных записей. Метки хранятся как float32. Пара без доступных меток исключается с подсчётом; отсутствие исходного события для подготовленной цели вызывает ошибку.

Предварительная сверка обнаружила метки у всех 68 451 исходных train-пар и 5 840 validation-пар. Есть 5 217 и 444 событий с нулевой долей, 449 и 32 со значением выше 100%. До ограничения диапазон — 0–159 и 0–154 соответственно. Эти сведения получены при аудите данных, до обучения.

Прогноз условен на наблюдаемое прослушивание. Он не является вероятностью клика, откликом на произвольный показ, удовлетворённостью или причинным вкладом трека в возвращение. Обучение включает organic и recommendation-driven события; флаг источника используется только для диагностики. Экспозиции и вероятности исторической политики отсутствуют, поэтому смещение наблюдаемых взаимодействий не устраняется.

## Временное разбиение

Каталог 2 000 треков, исходные запросы, пользователи и контексты сохраняются. Все события текущего timestamp исключены из истории. Цели нескольких треков одного запроса остаются отдельными размеченными парами; ни одна пара запроса не пересекает временную границу.

Исходный policy train делится по 80%-квантилю timestamp **запросов** (`inverted_cdf`, без случайного перемешивания):

1. `train`: timestamp ≤ границы; только эти метки используются для обучения модели и всех контролей.
2. `selection`: граница < timestamp ≤ исходного train end; используется для выбора эпохи по MSE.
3. `validation`: прежние policy validation-запросы после исходного train end; прогнозируется один раз после выбора checkpoint.

Каталог и его длительности уже построены на полном исходном policy train. Внутренняя selection не является оценкой с независимо построенным ранним каталогом. Метки validation в обучение и выбор эпохи не входят. Эта validation уже использовалась для выбора базовой GPT-2; она не заменяет финальный test.

Test-метки не извлекаются. Проверяется только контрольная сумма существующего test-файла. Прежние данные, модели и отчёты не перезаписываются; reward-данные сохраняются отдельно.

## Модель и обучение

Независимая сеть `CompletionReward` со случайной инициализацией. Веса GPT-2 не используются. Входы:

- Среднее embedding прошлых треков и embedding последнего трека; BOS/PAD не входят в среднее, UNK сохраняется.
- Embedding кандидата и произведение embedding кандидата на среднее истории.
- Embedding ID пользователя; словарь строится только по reward train. Для неизвестного пользователя — нулевой embedding.
- Длительность кандидата из train-каталога: стандартизованный log1p с ограничением ±3 и признак наличия длительности.
- Наличие кандидата в доступной истории, длина контекста и доля UNK.

Фактическая доля прослушивания кандидата и `is_organic` не являются признаками. История представляется средним и последним объектом; полный порядок событий модель не кодирует. Размер item embedding 64, user embedding 32; MLP 128 → 64 → sigmoid, GELU и dropout 0.1. Sigmoid ограничивает прогноз диапазоном [0, 1]. ID пользователя учитывает устойчивые индивидуальные различия, поэтому контроль по пользователю обязателен.

Один рецепт и seed 42. MSE по размеченным парам, AdamW, learning rate 0.001, weight decay 0.01, batch 256, clip gradient norm 1.0. Максимум 20 эпох, остановка после четырёх эпох без строго меньшего selection MSE. Выбирается минимальный selection MSE; при равенстве — более ранняя эпоха. Scheduler, подбор гиперпараметров и выбор лучшего seed не предусмотрены. Каждый запуск начинается с нуля.

После остановки загружается выбранный checkpoint и выполняется validation. Результат validation не используется для выбора иной эпохи или скрытого повторного подбора рецепта. При слабом качестве это фиксируется как результат; дальнейшее изменение потребует отдельного протокола.

## Контроли и метрики

Три контроля обучаются только по reward train: общая средняя доля, средняя по треку и средняя по пользователю. Для неизвестных групп — общая средняя. Все варианты оцениваются на одинаковых размеченных парах.

Основная метрика — MSE, меньше лучше. Дополнительные: RMSE, MAE, R², Pearson, средняя ошибка/прогноз/метка, MSE с равным весом пользователей. MSE для дробной метки не называется Brier score. Калибровка описывается средними прогнозами и метками в десяти фиксированных интервалах [0, 1].

Разрезы: train-каталожные тертили длительности, источник взаимодействия, известный/неизвестный пользователь и трек, повтор кандидата из доступного контекста. Полный каталог не размечен по доле прослушивания, поэтому эти регрессионные метрики не оценивают качество прогноза для всех возможных рекомендаций.

## Артефакты и воспроизведение

Из корня проекта с активным окружением:

```bash
python -m recsys_rl reward-prepare data/raw/yambda-50m-multi_event.parquet
python -m recsys_rl reward --device auto
python -m recsys_rl reward-audit
```

Подготовка: `data/processed/reward-v1/manifest.json` и массивы train/selection/validation. Обучение: `outputs/reward-v1/reward.pt`, prediction-списки selection/validation, история и summary. Checkpoint содержит параметры, словарь пользователей и статические признаки длительности. На macOS запуск дополнительно измеряется `/usr/bin/time -l`; его RSS/footprint не равны полному пику MPS или системы.

Метрики и контроли пересчитываются по сохранённым prediction-спискам, сверяются population и правило выбора эпохи. Проверяются хеши кода, конфигурации, протокола, исходных и подготовленных данных, исходной политики и артефактов. Непустые каталоги не перезаписываются. Продолжение незавершённого обучения не реализовано; для повтора задаются новые output-каталоги.

После сверки публикуются агрегированные JSON подготовки и результата в `experiments/`; данные, прогнозы отдельных событий и веса остаются локальными. Затем отдельно фиксируется эксперимент RL, включая ограничения изменения политики, варианты reward и rollout пяти объектов.

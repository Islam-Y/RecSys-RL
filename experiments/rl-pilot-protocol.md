## Гипотеза

Оптимизация фиксированного reward-прокси может повысить его прогноз, одновременно ухудшая next-item релевантность, разнообразие или устойчивость генерации. Проверка reward model не установила надёжное различение кандидатов: validation pairwise accuracy 51.65%, user-cluster интервал включает 50%. Поэтому пилот исследует компромисс и ошибки прокси; он не должен объявлять рост прогноза улучшением пользовательского опыта.

## Метод и границы

Первый пилот — **контекстный бандит с моделью вознаграждения**. Состояние — исходная история пользователя, действие — один из 2 000 треков. Для фиксированных историй максимизируется:

`J = mean_h [sum_i pi_theta(i|h)*r(h,i) - beta*sum_i pi_theta(i|h)*log(pi_theta(i|h)/pi_ref(i|h))]`.

Сумма и градиент вычисляются по всему ограниченному каталогу. В этом масштабе можно исключить вариацию от сэмплирования действий. Обучаются параметры GPT-2; reward model и исходная политика заморожены. Это модельная оптимизация офлайн-прокси без взаимодействия с пользователем. Переходы между состояниями и долгосрочный return в обучающую цель первого пилота не входят.

Для положительного beta существует контрольный оптимум на каждом состоянии: `pi_star(i|h) ∝ pi_ref(i|h)*exp(r(h,i)/beta)`. Формула KL-регуляризованной задачи приведена в [Rafailov et al., уравнения 3–4](https://arxiv.org/html/2305.18290v3#S4); здесь она используется как аналитический контроль для нейросетевого дообучения. При beta = 0 контроль — максимум reward. Аналитическое перераспределение вероятностей не считается обученной RL-моделью.

Выбирается последняя эпоха, промежуточная validation не управляет остановкой. Все 5 000 исходных validation-запросов оцениваются после обучения варианта. Фактическое время и память измеряются отдельно; равное число эпох не означает равные вычислительные затраты.

## Reward и шесть вариантов

`p(h,i)` — raw reward model. `u(user)` — ранняя пользовательская средняя с глобальным fallback. Калибровка и смесь зафиксированы по reward selection:

- `c = clip(0.7548164607*p + 0.1342643037, 0, 1)`.
- `hybrid = u + 0.4723990080*(c-u)`.
- `time = hybrid * min(duration_i, D95)/D95`, где D95 — 95%-квантиль длительностей train-каталога, для неизвестной длительности — его медиана. Это прокси доли прослушивания, умноженной на ограниченную длину трека; перемотки сверх 100% не учитываются.

| Вариант | Reward | Beta для KL |
|---|---|---:|
| raw-stress | p | 0 |
| raw-kl | p | 0.1 |
| raw-strong-kl | p | 1.0 |
| hybrid-matched-kl | hybrid | 0.0356574547 |
| time-kl | time | 0.1 |
| time-strong-kl | time | 1.0 |

Больший beta сильнее удерживает вероятности около исходной GPT-2. Вариант без KL — стресс-контроль и не кандидат для принятия в качестве основной политики.

**Проверка масштаба.** Для текущих коэффициентов clipping калибровки не активируется на любом p ∈ [0, 1]. Hybrid имеет вид `s*p + constant(user)`, `s = 0.3565745473`. При `beta_hybrid = s*beta_raw` аналитические оптимальные политики должны совпадать; допустимая численная разница ≤ 1e-5. Это отделяет улучшение калибровки от простого изменения силы регуляризации. Конечные траектории обучения сети могут различаться из-за численной точности и оптимизатора. Коэффициенты в коде берутся полностью из JSON результата проверки, а не из округлений этого текста.

Reward типа time намеренно меняет предпочтения по длительности. Он не считается долгосрочной удовлетворённостью и не штрафует короткие треки по психологическим предположениям.

## Сравнение и выбор

Обязательные контроли: исходная GPT-2, train-популярность, недавние треки + популярность, прямое ранжирование по reward и аналитическое KL-перераспределение. Обученные модели сравниваются на одинаковых запросах по:

- Recall/NDCG @5/10/20.
- Среднему raw/hybrid/time reward top-10 с одинаковым весом позиций; это общий прокси для всех списков, включая контроли.
- Ожидаемому reward полной softmax-политики, KL и энтропии; эти величины отделяются от среднего reward списка.
- Охвату каталога, концентрации, повторам, длительности и разрезам качества для известных/новых reward train пользователей и треков.
- Доле ожидаемого reward от объектов с малой обучающей поддержкой; рост этой доли рассматривается как сдвиг распределения, а не установленный reward hacking.

Фактическая доля прослушивания известна только для наблюдавшихся объектов. Метрики на совпадениях с рекомендованным списком сопровождаются числом совпадений и покрытием; им не присваивается смысл несмещённой оценки отклика новой политики. Без экспозиций и propensity логирующей политики нельзя заявлять корректную IPS-оценку.

Кандидат для итогового сравнения выбирается среди вариантов с KL: NDCG@10 ≥ 95% исходной GPT-2 и hybrid reward top-10 выше исходного; из допустимых — максимальный hybrid reward, при равенстве — более ранний вариант таблицы. Порог 95% — исследовательский допуск первого пилота, не продуктовый SLA. Если допустимого варианта нет, сохраняется исходная GPT-2.

Выбранный кандидат дополнительно обучается с seeds 43 и 44; меняется порядок батчей, исходный checkpoint и набор историй сохраняются. Он заменяет baseline для итогового сравнения только при выполнении допуска и прироста прокси на всех трёх seeds. Итоговый checkpoint — seed 42. Максимум пилота — восемь обучений. Парные интервалы различий считаются по user-cluster bootstrap; уже использованная validation сохраняет адаптивность подбора.

## Генерация пяти объектов

По seed 42 выбираются одинаковые 1 000 validation-историй. Для исходной GPT-2 и шести вариантов выполняются greedy- и sampled-rollout длины 5. В sampled-режиме используются общие заранее сгенерированные uniform-числа для уменьшения вариации сравнения. На каждом шаге выбранный ID добавляется в контекст, сохраняются BOS и последние 64 события. Уникальность треков искусственно не навязывается.

Добавленный объект — **синтетическое прослушивание**. Модель не знает, принял ли пользователь рекомендацию. Изучаются reward по шагам, повторы/зацикливание, длительность, концентрация, изменения контекста и доли UNK. Генерация не создаёт фактических меток и не доказывает качество пяти реальных взаимодействий. В первом пилоте это проверка переноса одношаговой цели на последовательную выдачу; обучение многошаговому return остаётся отдельным расширением.

## Долгосрочные цели

Подходящие будущие сигналы Yambda — наблюдаемое продолжение прослушиваний и возвращение после паузы. Для отдельного исследования можно задать продолжение в пределах 30 минут и возвращение в интервале от 24 часов до 7 суток. Нули допустимы только при полностью наблюдаемом окне до временной границы; иначе пример цензурируется. В событиях нужно учитывать весь доступный каталог пользователя, а не только 2 000 выбранных треков.

Эти метки отражают наблюдаемую активность и могут зависеть от устойчивых привычек пользователя. Они не устанавливают вклад рекомендуемого трека в возвращение. Офлайн проверяются предсказуемость, калибровка и чувствительность к срезам; причинный эффект и удовлетворённость потребуют проверки на пользователях. В текущем пилоте такая reward model не обучается.

## Контроль выполнения

До запуска фиксируются код, конфигурация, протокол и хеши. Сохраняются reference/cache-прогнозы, веса дообученных GPT-2, ranking-списки и rollout-ID. Кэш полного каталога сверяется с исходным forward reward model на наблюдавшихся парах; исходная GPT-2 должна воспроизвести прежние ranking-метрики. Вычисления и правило выбора пересчитываются по сохранённым артефактам. При нехватке ресурсов бюджет не сокращается скрыто: изменение фиксируется до перезапуска.

Финальный test остаётся закрытым до завершения выбора RL-настроек. Методологический ориентир по компромиссу accuracy/beyond-accuracy — [GPTRec](https://arxiv.org/abs/2403.04875); основание отдельно контролировать ошибки прокси — [Gao et al.](https://arxiv.org/abs/2210.10760). Наш пилот не является воспроизведением их результатов.

Кэш reward вычисляется пакетами по 32 истории с общими промежуточными вычислениями для кандидатов. Он должен совпасть с исходными прогнозами на наблюдавшихся парах с абсолютной погрешностью ≤ 2e-6. Пакет GPT-2 inference — 128, как у выбранного baseline. Аудит сохранённых весов повторяет inference и требует совпадения top-20 и максимальной погрешности logits ≤ 1e-5. Действия и reward всех rollout повторно вычисляются из сохранённых весов и общих случайных чисел.

```bash
python -m recsys_rl rl --device auto --prepare-only
python -m recsys_rl rl --device auto --resume
python -m recsys_rl rl-audit --device auto
```

`--resume` допускает только те же хеши кода, данных, конфигурации и протокола. Полностью сохранённые запуски проверяются и переиспользуются; незавершённые нужно сохранить отдельно перед повтором. Продолжение оптимизатора с середины обучения не реализовано. Для нового независимого повтора задаётся другой `--output-dir`.

Время и память `/usr/bin/time -l` относятся ко всему процессу: отдельно к подготовке кэша и всему пилоту. Внутреннее время каждого варианта сохраняется, но отдельный пик памяти процесса для каждого варианта не измеряется. Test-файл проверяется только по хешу.

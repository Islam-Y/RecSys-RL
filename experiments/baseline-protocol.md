# Протокол первого этапа: последовательная модель без RL

Зафиксирован 13 октября 2026 года до первого обучения. Настройки: `configs/mvp.json`.

## Цель и границы

Получить работающий контроль next-item prediction для будущего сравнения с RL. Продуктовая цель — удовлетворённость пользователя, продолжение взаимодействия и возвращение. Этот первый этап оценивает предсказание следующего наблюдавшегося прослушивания; он не доказывает удовлетворённость или рост возвращаемости.

Психологическое объяснение предпочтений через дофамин не исследуется: в данных таких измерений нет. Короткий трек допускается наравне с остальными. Изменение длительности рекомендаций и метрик по группам длительности входит в последующий анализ RL.

## Данные и время

- Источник: [Yambda-50M](https://huggingface.co/datasets/yandex/yambda), `flat/50m/multi_event.parquet`. SHA-256 исходного файла записывается при подготовке.
- Последовательность состоит из всех событий `listen` с валидными ID и временем. Доля воспроизведения не используется для выбора позитивов на этом этапе. Событие прослушивания не приравнивается к лайку.
- Глобальные границы времени: 70-й и 85-й дискретные процентили timestamp всех прослушиваний. Train включает время до первой границы, validation — следующий период до второй, test — оставшийся. Это собственное разбиение, не официальный benchmark Yambda.
- Timestamp задан в секундах; шаг квантования 5 секунд не означает умножение на 5.
- 1 000 пользователей выбираются детерминированно по хешу ID и seed среди имеющих не менее 50 событий в train. Частоты, состав каталога и длительность треков определяются только по их train-истории.
- Каталог — 2 000 наиболее частых train-треков. Объекты вне каталога сохраняются в контексте как UNK. Оценка условная на попадание следующего объекта в каталог; покрытие исходных событий публикуется отдельно.
- Запрос — пара `(user_id, timestamp)`. При нескольких прослушиваниях в одну секунду положительные цели образуют множество. Все события этого timestamp исключены из входного контекста. Произвольный порядок внутри квантованного времени не трактуется как следующий шаг.
- Вход: BOS и последние 64 события строго раньше T. Нужно не менее 5 прежних событий. Внутри уже прошедшего timestamp события упорядочены по item ID для воспроизводимости; настоящий порядок внутри 5 секунд неизвестен.
- До 60 000 train-запросов и по 5 000 validation/test-запросов выбираются по детерминированному хешу до проверки минимальной истории. Короткие истории затем исключаются; фактическое число запросов фиксируется.
- В validation разрешена реальная история до текущего T, включая ранее наблюдавшиеся validation-события. Параметры модели по этой истории не обновляются.

## Модель и оценка

- Официальная реализация GPT-2 из Transformers, случайная инициализация; токены — ID треков, без текстового токенизатора или предобученных языковых весов.
- 2 decoder-блока, размер 128, 4 головы, causal attention, обучаемые позиции и связанные входные/выходные embeddings. Конфигурация задана заранее для локальных 16 ГиБ памяти.
- Предсказываем цели T по последнему скрытому состоянию контекста. Loss — средняя cross entropy по всем положительным целям запроса. PAD/BOS/UNK не являются рекомендательными кандидатами.
- 3 эпохи AdamW; лучший checkpoint выбирается по validation NDCG@10. Seed, параметры и ограничения сохранены в конфигурации. Test-метрики на этом этапе не рассчитываются.
- Ранжируется весь ограниченный каталог, без сэмплирования негативов. Ранее прослушанные треки разрешены: повторное прослушивание музыки может быть целевым действием.
- Контроли: популярность на train и последние уникальные треки пользователя из того же доступного контекста; недостающие места recency-контроля заполняются train-популярностью.
- Recall и NDCG @5/10/20 усредняются по запросам с множеством положительных целей. Равные score разрешаются по порядку token ID.
- Диагностики @10: охват каталога, концентрация показов топ-10 наиболее выдаваемых объектов, доля повторов из контекста, средняя длительность рекомендаций. Релевантность дополнительно разбивается по train-тертилям длительности целевого трека; смешанные запросы выделяются отдельно.

## Следующие этапы

1. Reward model: оценить отклик по истории и кандидату на отдельном временном периоде. Проверить прогноз доли прослушивания, ошибки по длительности и популярности, чувствительность к объектам вне обучавшего распределения. Лайки, дизлайки и наблюдаемое продолжение/возвращение рассмотреть как дополнительные сигналы; отсутствие лайка не считать дизлайком.
2. До просмотра финального test зафиксировать RL-метод, функции вознаграждения, ограничения KL и бюджет подбора. Сравнивать копии одного baseline checkpoint на одинаковых запросах и каталогах.
3. Сравнить один шаг и rollout пяти объектов. Сгенерированный объект в контексте не означает реальное прослушивание; offline rollout без модели отклика не воспроизводит поведение пользователя.
4. Возвращение через заданный горизонт требует полного наблюдения этого горизонта: примеры у конца периода исключать или учитывать цензурирование. Возвращаемость остаётся косвенным сигналом; причинный эффект новых рекомендаций требует отдельной проверки.
